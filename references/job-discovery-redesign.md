# Job Discovery 중심 개편 설계안

## 1. 개편 목적

현재 `Role Discovery`는 새 직무를 발견하는 기능과 실제 채용 공고를 수집하는 기능을 한 흐름에서 처리한다. 이 때문에 하나의 공고를 저장하려면 직무 후보에 필요한 독립 근거, 정확한 직무명 통합, 승인 상태까지 충족해야 한다. 실제 취업에 활용할 공고가 누락되고, 직무 변화에 대응하기 위한 분류도 공고 저장을 막는 조건으로 작동한다.

개편 뒤 제품은 다음 두 기능과 두 Notion DB로 구성한다.

1. `Job Discovery`: 대한민국 근무 채용 공고를 찾고, 공고 본문에서 직무를 인식해 Jobs DB에 저장한다.
2. `Trend Update`: AI·Security·AI × Security 분야의 국내외 동향을 수집해 Trends DB에 저장한다.

별도의 Roles DB, `Role Discovery`, Candidate 승인·거절 흐름은 제거한다. 직무 인식은 Job Discovery의 분류 단계로 유지하되, 미리 등록된 직무명과 일치해야 공고를 저장할 수 있는 허용 목록으로 사용하지 않는다.

## 2. 책임 분리

| 구분 | Job Discovery | Trend Update |
| --- | --- | --- |
| 목적 | 지원하거나 관찰할 대한민국 채용 공고 수집 | AI·Security·AI × Security 분야 변화 파악 |
| 주요 출처 | 기업 공식 채용 페이지, Saramin, JobKorea, Wanted, Jumpit 등 | 공식 문서, 기업·기술 블로그, 보도자료, 보고서, 논문, 뉴스, GitHub 등 |
| 지역 범위 | 원문에서 대한민국 근무 확인 필수 | 비채용 정보는 해외 포함, 채용 자료는 대한민국 근무만 허용 |
| 저장 단위 | 채용 공고 한 건 | 원문 콘텐츠 한 건 |
| 직무 정보 | 공고 원문 제목을 보존하고 본문에서 인식 | 콘텐츠가 영향을 주는 직무 유형을 분류 |
| 상호 의존성 | Trend 상태나 승인 여부에 의존하지 않음 | Jobs DB 상태나 승인 여부에 의존하지 않음 |

## 3. Job Discovery 처리 흐름

### 3.1 검색

검색은 AI, Security, AI × Security의 세 탐색 경로를 유지한다. 이 구분은 검색 누락을 줄이기 위한 경로이며 저장 허용 목록이 아니다.

- 직무명 검색: 한국어·영어의 대표 직무명과 실제 공고에서 새로 확인한 표현을 사용한다.
- 업무 검색: LLM·agent·RAG·model serving·evaluation과 취약점 분석·위협 모델링·IAM·보안 평가·거버넌스 같은 업무·기술 조합을 사용한다.
- 출처 검색: 기업 공식 채용 페이지를 먼저 확인하고 국내 채용 플랫폼을 출처별로 확인한다.
- 한 번의 실행에서 새로 인식한 표현은 결과에 기록하되 검색 범위를 재귀적으로 계속 확장하지 않는다. 검토 후 다음 실행의 검색어 후보로 사용한다.
- 검색 완료 보고에는 출처별 질의 수, 확인한 검색 결과 수, 원문을 연 공고 수와 접근 실패를 포함한다. 정해진 최소 후보 수를 맞추기 위해 공고를 추측하지 않는다.

### 3.2 공고 사실 확인

다음 항목은 공고 원문 또는 기업이 관리하는 원본 공고에서 확인한다.

- 회사명과 원문 공고명
- 대한민국 근무지 또는 대한민국 고용 가능 여부
- 주요 업무와 자격 요건 중 확인 가능한 내용
- 신입, 경력, 신입·경력 또는 미확인인 경력 수준
- 게시일, 마감일과 모집 상태 중 원문에 표시된 값
- 원문 URL과 확인된 canonical URL

대한민국 근무지가 불명확한 공고는 제외한다. 원문에 게시일이 없더라도 현재 모집 중임을 확인할 수 있으면 `게시일 미확인`으로 별도 보류·저장 후보에 포함한다. 이 공고는 “최근 한 달 게시 공고” 수에는 포함하지 않는다.

### 3.3 관련성 판단과 직무 인식

관련성 판단은 공고 제목보다 주요 업무와 자격 요건을 우선한다.

- `AI`: 모델·데이터·LLM·agent·AI platform의 개발, 운영, 평가 또는 적용이 핵심 업무인 공고
- `Security`: 애플리케이션·제품·클라우드·IAM·보안 운영·보안 연구·거버넌스가 핵심 업무인 공고
- `AI × Security`: AI 시스템의 보안, AI를 활용한 보안, 모델·agent의 공격과 방어, AI 위험·안전·거버넌스가 핵심 업무인 공고

공고 원문 제목은 바꾸지 않고 `인식한 직무`를 별도로 기록한다. 인식한 직무는 검색과 필터링을 위한 설명값이며, 새로운 표현이더라도 저장을 막지 않는다. 분류가 모호하면 `검토 필요`로 저장 후보에 남기고 판단 근거를 기록한다.

관련성은 다음과 같이 표시한다.

- `높음`: 제목 또는 핵심 업무에서 해당 분야가 명시되고 본문 근거가 충분함
- `중간`: 제목은 일반적이지만 주요 업무나 자격 요건에서 해당 분야 업무가 확인됨
- `검토 필요`: 일부 신호는 있으나 원문 접근 제한이나 설명 부족으로 확정하기 어려움
- `제외`: 회사나 제품에 관련 단어만 있고 실제 직무 업무와 연결되지 않음

`검토 필요`는 사용자에게 보여주되 자동으로 버리지 않는다. `제외`만 Jobs DB 저장 대상에서 제외한다.

### 3.4 저장 기준

공고 한 건을 저장하는 데 두 번째 독립 출처나 별도의 정보글을 요구하지 않는다. 접근 가능한 공고 원문 한 건에서 대한민국 근무지와 관련 업무를 확인하면 저장할 수 있다.

기간 요청은 다음처럼 처리한다.

1. 게시일이 기간 안인 공고: 확정 결과
2. 게시일은 없지만 현재 모집 중인 공고: 게시일 미확인 결과
3. 게시일이 기간 밖인 공고: 기간 밖으로 제외
4. 게시일과 모집 상태를 모두 확인할 수 없는 공고: 검토 필요 또는 제외 사유로 보고

하나의 공고 오류가 다른 정상 공고의 저장을 막지 않는다. 각 공고를 `저장`, `검토 필요`, `제외`, `중복`으로 독립 판정하고 결과를 모두 집계한다.

### 3.5 중복 판정

중복은 직무가 아니라 채용 공고 단위로 판정한다.

우선순위는 다음과 같다.

1. 같은 canonical URL 또는 정규화한 원문 URL
2. 같은 채용 플랫폼의 공고 ID
3. 회사명·원문 공고명·근무지·게시일 또는 마감일이 모두 일치하는 동일 채용 건

같은 회사와 같은 제목이어도 게시 시점, 근무지 또는 공고 ID가 다르면 별도 공고로 남긴다. 여러 플랫폼에 복제된 동일 공고는 Jobs DB 한 행에 대표 원문 URL과 추가 확인 URL을 함께 보존한다.

## 4. Jobs DB 설계

Jobs DB의 한 행은 하나의 채용 공고를 뜻한다.

| 속성 | 형식 | 용도 |
| --- | --- | --- |
| 공고명 | Title | 원문에 표시된 정확한 채용 공고명 |
| 회사명 | Rich text | 채용 기업명 |
| 인식한 직무 | Rich text | 본문 업무를 바탕으로 설명한 직무 유형 |
| 직무 분야 | Select | AI, Security, AI × Security |
| 관련성 | Select | 높음, 중간, 검토 필요 |
| 경력 수준 | Select | 신입, 경력, 신입·경력, 미확인 |
| 주요 업무 | Rich text | 원문에서 확인한 핵심 업무 |
| 자격 요건 | Rich text | 필수·우대 요건 중 확인한 내용 |
| 기술 키워드 | Multi-select | 검색과 필터링에 사용할 기술·업무 키워드 |
| 근무지 | Rich text | 대한민국 내 원문 근무지 |
| 고용 형태 | Select | 정규직, 계약직, 인턴, 기타, 미확인 |
| 근무 방식 | Select | 출근, 하이브리드, 원격, 미확인 |
| 게시일 | Date | 원문에서 확인한 게시일, 없으면 비워 둠 |
| 마감일 | Date | 원문에서 확인한 마감일, 없으면 비워 둠 |
| 모집 상태 | Select | 모집 중, 마감, 미확인 |
| 관심 상태 | Select | 신규, 관심, 지원 예정, 지원, 제외 |
| 출처명 | Rich text | 기업 채용 페이지 또는 채용 플랫폼명 |
| 원문 URL | URL | 대표 원본 공고 URL |
| 추가 확인 URL | Rich text | 동일 공고의 복제본과 보조 확인 URL |
| 수집일 | Date | Job Discovery 실행일 |
| 판정 근거 | Rich text | 관련성·직무 분야·검토 필요 판단 근거 |
| 메모 | Rich text | 접근 제한, 게시일 미확인 등 사용자 검토 사항 |

`인식한 직무`는 자유롭게 갱신할 수 있는 텍스트로 시작한다. 직무명이 안정되고 반복 패턴이 충분히 쌓인 뒤에만 별도의 표준 직무 목록이나 선택형 속성을 검토한다.

## 5. Trends DB 설계

Trend Update는 Jobs DB의 승인 상태를 요구하지 않고 AI·Security·AI × Security 분야 자체를 검색한다.

| 속성 | 형식 | 용도 |
| --- | --- | --- |
| 제목 | Title | 원문 제목 |
| 요약 | Rich text | 사실 중심의 간결한 요약 |
| 핵심 시사점 | Rich text | 취업 준비와 직무 변화 관점의 의미 |
| 출처 유형 | Select | 기존 14개 출처 유형 유지 |
| 출처명 | Rich text | 발행자 또는 기관 |
| 원문 URL | URL | 원본 출처 URL |
| 게시일 | Date | 원문에서 확인한 게시일 |
| 수집일 | Date | Trend Update 실행일 |
| 관련 분야 | Multi-select | AI, Security, AI × Security 중 하나 이상 |
| 관련 직무 | Multi-select | 콘텐츠에서 영향을 받는 직무 유형 |

현재 `관련 직무`의 Roles DB relation은 제거하고 Multi-select로 바꾼다. Jobs DB의 개별 공고는 일시적인 채용 건이므로 Trend 항목의 필수 관계로 사용하지 않는다.

## 6. Agent 구조 개편

현재 세 영역 조사 Agent는 Job Discovery의 검색 Agent로 역할을 바꿀 수 있다.

- `ai_job_researcher`: AI 공고 검색
- `security_job_researcher`: Security 공고 검색
- `ai_security_job_researcher`: AI × Security 공고 검색
- `job_evidence_reviewer`: 원문 접근성, 대한민국 근무지, 중복 공고와 관련성 근거 검토

검색 Agent는 근거 2개를 만들거나 직무 후보를 확정하지 않는다. 확인한 공고와 제외·보류 사유를 빠짐없이 반환한다. 검토 Agent의 flag는 해당 공고만 `검토 필요`로 보내며 전체 실행을 실패시키지 않는다. 부모 workflow가 공고별 판정과 Jobs DB 쓰기를 담당한다.

Trend Update는 별도의 검색 흐름을 유지하며 Jobs DB snapshot이나 관심 상태를 입력으로 요구하지 않는다.

## 7. 기존 데이터 이전

실제 Notion 변경 전에 읽기 전용으로 현재 data source와 행을 다시 조회하고 이전 계획을 보여준다.

1. 현재 Roles DB의 각 행이 실제 공고 근거를 가진 경우 Jobs DB 속성으로 변환한다.
2. 현재 1건인 `기술 보안 엔지니어 채용`은 원문 공고명, Security 분야, 경력 수준, 서울 근무지, 업무, URL과 기존 메모를 보존해 Jobs DB 후보 행으로 이전한다.
3. 직무 개념만 있고 특정 공고가 없는 Roles 행은 Jobs DB에 억지로 넣지 않고 보관 페이지에 유지한다.
4. Trends DB의 기존 항목은 보존하면서 `관련 직무` relation을 새 Multi-select 값으로 옮긴다. 현재 운영 Trends DB가 비어 있다는 기록은 실제 변경 직전에 다시 확인한다.
5. 기존 Roles DB와 기존 View는 즉시 삭제하지 않고 `AI Security Career Tracker 보관` 페이지로 이동한다.
6. 이전 결과를 재조회해 행 수, URL과 핵심 텍스트가 일치한 뒤에만 운영 화면을 Jobs·Trends 탭으로 바꾼다.
7. 로컬 설정은 `roles_data_source_id`에서 `jobs_data_source_id`로 명시적으로 이전한다. 한쪽만 확인되거나 값이 충돌하면 새 DB를 만들거나 기존 값을 덮어쓰지 않는다.

## 8. 구현 단계와 완료 기준

### 단계 1: 계약과 순수 Python 경계 변경

- Job Observation, 공고별 판정, 직무 인식, 기간 상태와 중복 판정 모델 구현
- 정상 공고와 불완전 공고가 함께 있어도 정상 공고가 처리되는 시험 추가
- 공고 원문 한 건만으로 저장 가능한 시험 추가
- 동일 제목의 서로 다른 채용 건과 여러 URL의 같은 채용 건을 구분하는 시험 추가

### 단계 2: Job Discovery Agent와 Skill 개편

- 세 조사 Agent와 종합 검토 Agent의 이름·입출력 계약 변경
- 검색량과 출처별 탐색 기록, 제외·보류 사유 보고 추가
- Role Discovery와 Candidate 승인·거절 호출 제거

### 단계 3: Notion schema와 데이터 이전

- 실제 변경 전 Jobs DB 생성·이전 계획을 사용자에게 제시
- 승인된 계획으로 Jobs DB와 Trends DB schema 변경
- 기존 데이터 보존, 설정 이전과 운영 View 갱신 후 재조회

### 단계 4: 비교 실사용 시험

같은 기간과 같은 출처 범위를 사용해 기존 방식과 새 Job Discovery를 비교한다.

- 검색 결과 수
- 원문 확인 공고 수
- 대한민국 근무 확인 공고 수
- 저장, 검토 필요, 제외와 중복 건수
- 확인된 적격 공고 중 누락된 비율
- 관련 없는 공고가 포함된 비율
- 공고 수와 인식한 직무 수

완료 조건은 결과 건수를 임의로 늘리는 것이 아니다. 검색 범위와 제외 사유를 재현할 수 있고, 확인된 적격 공고를 구조적 이유로 버리지 않으며, 모든 저장 행이 하나의 실제 대한민국 채용 공고를 가리켜야 한다.

## 9. 이번 설계에서 확정할 제품 결정

- 운영 DB는 Jobs DB와 Trends DB 두 개만 사용한다.
- 별도 Roles DB와 직무 Candidate 승인·거절은 제거한다.
- 직무 인식은 Job Discovery 안에서 수행하고 공고 저장을 막는 사전 허용 목록으로 사용하지 않는다.
- 공고 한 건은 확인 가능한 원문 한 건으로 저장할 수 있다.
- 게시일 미확인 공고는 최근 기간 결과와 구분해 보여준다.
- Trend Update는 Jobs DB 상태와 독립적으로 AI·Security·AI × Security 분야를 검색한다.
